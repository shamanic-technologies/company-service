## An org's brand identity is its FIRST claim, and it is answered by an indexed batch read — never by the full catalogue

`POST /internal/brands/identity-by-org` (`src/services/orgBrandIdentityService.ts`) answers "what brand identity belongs to these orgs?" — a display `name` plus the `domain` a logo is rendered from, and nothing else. The consumer (billing-service, naming the org whose conversion earned a pending referral reward) is showing a customer who referred them, not opening a window onto another customer's business, so **never widen this payload** with money, campaigns, performance, configuration, prospect PII, audiences, or the brand's other orgs.

**It is a BATCH read, and it must stay one indexed query.** `GET /internal/brands/all` is the whole-catalogue staff listing; answering one org from it is the bulk-reader antipattern — the work grows with the platform and is almost entirely wasted. `getBrandIdentitiesByOrgIds` is a single `DISTINCT ON (org_id)` over `org_brands` (hitting `org_brands_org_id_idx`) joined to `brands`, bounded by the ids asked for. Do not reimplement it on top of the catalogue listing, and do not let a caller fan out one request per org.

**An org with several brands resolves to the one it claimed FIRST** — `org_brands.claimed_at` ascending, ties broken by `brand_id` ascending so the order is total even when two claims share a timestamp. The first claim is the brand the org onboarded with, and the pick is *stable*: every brand claimed later leaves the answer untouched, so a referral reward keeps naming the same business for the life of the row. A "most recent" or "any" pick would let the displayed name drift under a customer looking at a months-old reward.

**Absence is the answer for an org with no brand.** No entry, no placeholder, no empty string — the caller renders nothing rather than something wrong. `resolveDisplayName` returns a stored name, else the titlecased domain (a deterministic derivation of data the brand actually has), else `null`; a row that identifies nothing is filtered out in SQL so the org still resolves via its NEXT claim rather than being lost to an unidentifiable first one. Do not add an `'Unknown'`-style fallback here.

**Internal only.** Service auth, org-less, deliberately not on `publicRouter` and not org-scopable by a customer — the caller legitimately holds org ids that are not its own. The batch rides in the BODY, not a query string, so org ids do not land in access logs and proxy traces. Regression: `tests/integration/orgBrandIdentity.test.ts`, `tests/unit/orgBrandIdentity.test.ts`.

## A domain belongs to whoever CHECKED OUT on it — brand-service never computes checkout itself

Owner decision (Kevin, 2026-07-29). `brands.domain` is globally unique, so attaching a website to a brand can collide with an existing holder row. The collision is NOT automatically a refusal:

- **Holder never checked out (by ANY org)** → the domain is up for grabs. It is MOVED onto the target brand; the holder is left as a **no-website brand** (`domain = url = NULL`) so any OTHER org still claiming it keeps a working identity. Never delete a holder row, never touch another org's `org_brands` membership.
- **Holder checked out by the CALLER's org** → 409 `DOMAIN_OWNED_BY_YOUR_PAID_BRAND`.
- **Holder checked out by ANOTHER org** → 409 `DOMAIN_OWNED_BY_ANOTHER_ORG`.

The two refusals MUST stay distinguishable by `code` (plus `domain` + `conflictingBrandId` on the body) — a dashboard renders different copy per case ("switch to your paid brand" vs "this domain isn't yours"). Do NOT collapse them back into one generic `DOMAIN_CONFLICT`.

**Checkout state is NOT ours to compute.** client-service owns the (org, brand) ↔ money join and derives it live from stripe + billing: `GET /internal/brands/{brandId}/checkout-status` → `{ brandId, status: 'checked_out'|'not_checked_out'|'no_org_claims_brand', checkedOut, orgs: [{ orgId, checkedOut, reason, ... }] }`. The paying orgs are the `orgs` entries with `checkedOut: true`. Never re-derive this from billing/stripe here, and never mirror it locally. Client: `src/lib/client-client.ts` (`CLIENT_SERVICE_URL` / `CLIENT_SERVICE_API_KEY`).

**Fail CLOSED, never fail open.** A network error / non-2xx / unparseable body from client-service throws `CheckoutStatusUnavailableError` → the route 502s. Defaulting to "nobody paid" would hand a paying org's domain to somebody else. There is deliberately no `?? false`, no 404-means-unpaid branch (client-service answers never-paid with a truthful 200, so a 404 means the route is wrong, not that the brand is free).

**Cleanup uses the EXISTING merge primitive** — `rewriteBrandReferences` in `src/services/brandMergeService.ts` (moved there out of `brands.routes.ts` so services can call it without importing a router). When the never-paid holder belongs to the CALLER's own org, its child rows are merged onto the target (target always wins on conflict) and the caller's `org_brands` row is deleted, so the abandoned shell stops polluting their brand list. The primitive now also carries the user-authored one-row-per-brand tables (`brand_business_context`, `brand_sales_economics`, `brand_click_destinations`, `brand_whatsapp_links`) and `brand_user_fields` — without them a merge silently strands confirmed user data on the abandoned row. `brand_transfers` (audit log) and `brand_relations` (PK(source,target), a rewrite can self-collapse an edge) are deliberately NOT rewritten. Reference: `tests/integration/domainTakeover.test.ts`.

## No-website brand identity is `(orgId, lower(name))` — creates are idempotent

A no-website brand has no domain to dedup on, so `createBrandWithoutWebsite` keys on the caller's org + the case-insensitive name and RETURNS the existing brand (`created: false`) instead of inserting. Re-running onboarding used to mint a fresh row every time — that is how one org accumulated three brands for one business. Two different names for one org stay distinct; two orgs with the same name stay distinct (no cross-org reuse — there is no shared domain identity to justify it). Regression: `tests/integration/noWebsiteBrandDedup.test.ts`.

## A brand's share credential is ABSENT by default, unguessable, and NEVER the conversion-tracking token

`brand_share_tokens` (PK = `brand_id`, `token` text NOT NULL UNIQUE, `org_id` uuid NOT NULL) holds the per-brand read-only SHARE credential: a customer mints one so somebody outside the org (investor, client, colleague) can open a read-only public brand page without signing in. Owner: `src/services/brandShareTokenService.ts`; routes: `src/routes/share-token.routes.ts`.

**Absent by default.** No row is created at brand create. A brand with no row is NOT shareable and nothing resolves — absence IS the state, so there is no `enabled` flag and no null-token row.

**One row per (org, brand), so rotate/revoke are the row's own semantics.** Each org that claims a domain shares its OWN view of it. Keyed on the brand alone, a second claiming org minting or rotating would silently invalidate the FIRST org's live share link — one org revoking another's credential on a brand it merely also claims. Rotating and revoking only ever touch the caller's own row. Regression: `tests/integration/brandShareToken.test.ts` ("two orgs claiming one brand each get their OWN credential"). Rotating overwrites `token` in place — that single UPDATE is exactly what makes the previous link stop resolving. Revoking DELETEs the row. Never add a second live credential per brand (a `SELECT ... WHERE token = $1` must stay a one-row exact match, and "rotate stops the old link" must stay true by construction, not by a sweep).

**The credential must not be derivable from anything the customer already exposes.** The brand id and the org id both sit in the customer's own address bar and in every support ticket they paste, so a link built from either is a one-line transform of a public string. `generateShareToken()` takes NO arguments: `bshr_` + `randomBytes(32).toString('base64url')`. Do not "improve" it into an HMAC/hash of the brand id, do not seed it from the clock, and do not encode the org id in it — the token stays an opaque random string, and everything a resolve answers with comes from the ROW it matches, never from the string. Regression: `tests/unit/brandShareToken.test.ts` pins the zero-arg signature + entropy.

**`org_id` records WHICH ORG SHARED THE BRAND, and it is written at MINT time, never derived on read.** The renderer of a shared page needs it because every figure such a page shows (outreach, audiences, leads, strategy) is served per-org — the credential alone tells it which brand to render and leaves it unable to fetch a single number. It cannot come from `org_brands`: 21 production brands are claimed by MORE than one org and 18 by NONE, so membership answers "ambiguous" or "nothing" exactly where one org is needed. The mint route is org-scoped and ownership-checked, so the writer already holds the answer — persist it (`createIfAbsent(brandId, orgId)` / `rotate(brandId, orgId)`, arity pinned by the unit test), do NOT add a read-time lookup or a fallback. **A rotate re-mints, so the row's org becomes the ROTATING org**: for a brand two orgs both claim, the link that resolves is the one minted last and it opens ITS view. The column is NOT NULL on purpose — the resolve must answer with one org or refuse, and a nullable column invites exactly the plausible-stand-in fallback this must never serve. Migration `0048` backfills legacy rows from the earliest `org_brands` claim (verified on a fork of production: the one pre-existing row attributed correctly, zero nulls, re-run idempotent).

**Do NOT reuse or extend the conversion-tracking token (lead-service).** That one is a WRITE credential for conversion ingest; putting it in a shared URL would let the link holder forge conversions. These are different credentials with different blast radii and must stay separate.

**The resolve is service-auth, takes no org IN, and answers with the org OUT.** `POST /internal/share-tokens/resolve` body `{ shareToken }` → `{ brandId, orgId, brand }`. It takes no org context by design (the caller is distribute's own server-side public-page renderer, which has not identified an org yet) and answers with one because learning it is the whole reason the renderer calls: `orgId` sits at the TOP LEVEL beside `brandId`, never inside `brand`, so the public brand payload is untouched and nothing a broader audience reaches gained a field. Service auth is enough — this deliberately is NOT reachable unauthenticated from the internet. The credential rides in the BODY, not the path, so it does not land in access logs and proxy traces. Unknown / revoked / rotated-away all return the same 404.

**`brand` is `getBrandDetail(..., { mode: 'platform' })` — the exact shape `GET /public/brands/:id` already serves.** Nothing new is exposed. Never widen this payload with money (spend, daily budget, cost per outcome, ROI, credits), prospect PII (lead names/emails), audiences, or the org id. If the public page needs more, it composes it from endpoints it already calls — a share credential does not unlock new data classes.

**NOT rewritten by `rewriteBrandReferences`** (the merge primitive), alongside `brand_transfers` / `brand_relations`. Moving a credential minted for an abandoned holder onto the target brand would silently widen what every existing link holder can see; the credential stays with the brand it was minted for. Regression: `tests/integration/brandShareToken.test.ts` (full lifecycle + cross-org 403 + "a credential minted for brand A never resolves to brand B" + a brand two orgs claim, where the credential names whoever minted it).

## A brand's colours come from the provider or nowhere, and the provider answers LATER

The dashboard renders each client in that client's OWN colours instead of our blue charter (owner-approved deviation). Nothing in the fleet stored a brand's colours, and brand-service is where they belong: it already owns brand identity (name, logo) and is already the one service that talks to logo.dev.

**`colors` is `string[] | null` on every brand read, and `null` is an ANSWER.** Provider-ordered hex strings (`["#000103","#ce2e36","#003366"]` for shockwavecenters.com), nothing pre-filtered or ranked — the consumer does its own selection, so picking one here would take a decision that is not ours. `null` means WE HAVE NO COLOURS for this brand, and the consumer falls back to its own charter on it: a wrong or invented colour is worse than none. So no colour is ever defaulted, guessed, or derived from the logo, the name or the domain, and a brand with no row, a row still pending and a row that gave up are all the same `null` — there is nothing to distinguish, in all three cases we have nothing to serve.

**The retrieval is DECOUPLED from the write that enqueued it, and that is the load-bearing property.** logo.dev's Brand endpoint is ASYNCHRONOUS for any domain it has not indexed: it answers `202 {"msg":"not found, looking up"}` and queues the domain on its side, so the palette exists only on a LATER call. Measured 2026-08-25 against the seven live client domains: ONE (shockwavecenters.com) returned 200 with colours, six returned 202 and were still 202 on a re-poll two minutes later. A design that requests and reads in the SAME run therefore stores nothing and never retries — the brand keeps an empty value forever. So `brand_colors` is a QUEUE (`enqueueBrandColors` at brand create, local insert, zero metered calls) and `refreshPendingBrandColors` (`src/services/brandColorsService.ts`) drains it on its own 6-hourly cadence. Do NOT collapse the two back into one call, and do NOT fetch on a brand READ.

**The volume is bounded HERE because the vendor will not tell us what is left.** That endpoint bills a SEPARATE prepaid credit grant (~100 calls/month on Community, NOT the monthly request pool the name-search endpoint uses), hard-fails 402 when exhausted, and exposes NO quota header. Four bounds, all of them deliberate: the work list is the QUEUE, never a sweep of `brands` (156 rows would blow a month's grant in one pass, and 149 of them are not live); a brand costs at most `MAX_ATTEMPTS` calls ever, then goes `unavailable`; a pass costs at most `PER_RUN_LIMIT`; a calendar month costs at most `MONTHLY_CALL_BUDGET`, counted off `logo_dev_brand_calls` — the meter the vendor does not give us. A 402 stops the pass on the spot and does NOT spend the brand an attempt (it got no answer). Never make this per-request or per-read.

**It authenticates with the SECRET key** (platform provider `logo-dev-secret`, `sk_...`). `logo-dev` holds the PUBLISHABLE `pk_...` that signs img.logo.dev URLs and does not authenticate this endpoint — the same trap as `lib/logo-dev-search.ts`. The key is resolved ONCE per pass, and a key we cannot read is a loud stop, not a silent no-op.

**Every failure resolves to "no colours", loudly.** 402, 202, network, non-2xx, unparseable body, and an indexed domain with an empty palette each have a named outcome, each logs, and each lands in `logo_dev_brand_calls`. `no_colors` is terminal (retrying cannot make a palette appear); `pending` and `failed` are retryable and both spend one bounded attempt. Nothing is swallowed and nothing falls back to a value.

**Colours follow the DOMAIN, so they move and die with it.** `brand_colors` is keyed on `brand_id` alone — identity, like `name` and `logo_url`, NOT `(org_id, brand_id)` like everything a customer configures: there is one palette per domain and two orgs claiming it see the same one. A brand that GAINS a domain (`updateBrandWebsite`) has its row reset to pending, because a palette held for another domain is another business's colours; a brand that LOSES its domain (the never-paid holder on the takeover path) has its row deleted rather than serving a stale one.

**The existing brands were enqueued once, by hand, and only the live ones.** `scripts/enqueue-live-brand-colors.ts` queues the seven live client domains (idempotent, dry-runnable, spends no metered call). New brands enqueue themselves at create, which is a volume the grant absorbs. Do not extend that script into a full sweep.

**api-service needs no change** — `/v1/brands/:id` and `/v1/brands` are pure `res.json(result)` passthroughs (verified against `origin/main`), so the field arrives at the gateway for free. Regression: `tests/unit/logoDevBrandColors.test.ts`, `tests/integration/brandColors.test.ts`.

brand-service has NO `buildInternalHeaders`/allowlist helper (unlike instantly-service). Each identity/tracking header (`x-org-id`, `x-user-id`, `x-run-id`, `x-campaign-id`, `x-feature-slug`, `x-brand-id`, `x-workflow-slug`, `x-audience-id`) is cherry-picked explicitly at every site. So adding a NEW tracking header means threading it through ALL of these, or it silently drops:

## The GOAL vocabulary is RETIRED — the sales funnel is the only word for what a brand sells through

**`src/services/salesFunnelCatalogue.ts` owns the vocabulary.** Seven tokens, and brand-service emits nothing else on any read:

    sales_meetings_from_conversation | sales_meetings_from_website
    website_purchases                | form_magnet
    sales_from_conversation          | sales_meetings_from_ads
    lead_forms_from_ads

**Why the goal died rather than living beside the funnel.** They were never equals: the funnel is strictly the richer word. `sales_meetings_from_conversation` and `sales_meetings_from_website` BOTH mapped onto one `meetingBooked`, so a meeting won from a reply and one won on the website were the same thing to every consumer, and features-service could not price them apart. Keeping both meant every consumer carried a translation layer for the poorer of the two words. The four keys were renamed in the same ship (`reply_meeting` → `sales_meetings_from_conversation`, `visit_meeting` → `sales_meetings_from_website`, `visit_signup` → `website_purchases`, `visit_form` → `form_magnet`) because prod carried 10 funnel rows and it was never going to be cheaper.

**`src/lib/goal-vocabulary.ts` is what survives, and it exists for WRITE TOLERANCE only.** Every goal spelling the fleet has ever sent is accepted FOREVER (the eight `RETIRED_GOALS` plus every entry of `LEGACY_OPTIMIZATION_GOALS`, including the pre-rename `purchase`), and each one resolves to the funnel(s) it named via `funnelKeysForRetiredGoal`. That tolerance is exactly what made the emission switch safe to make in one repo: no consumer had to change in lockstep. **Never delete an entry from either list**, and never add a read path that emits one. Same discipline for the funnel keys themselves — `toSalesFunnelKey` accepts the four pre-retirement spellings forever and stores the canonical one.

**The owner-approved goal→funnel mapping, and the two entries that are not one-to-one.** `websitePurchase`, `signup` and `websiteVisit` → `website_purchases`; `formSubmission` → `form_magnet`; `positiveReply` → `sales_meetings_from_conversation`. `meetingBooked` names BOTH meeting funnels, so it resolves on the one signal that tells them apart: a brand with a click destination is sending outreach onto its own site, so its meetings come from the WEBSITE; every other brand's come from the conversation. `combinedSales` becomes TWO declarations rather than a lossy pick — the model is multi-funnel, so the combined goal is expressible without loss. `whatsappConversation` names NOTHING (the catalogue has no whatsapp chain, and no brand in production carried it): `funnelKeysForRetiredGoal` answers `[]` and the write acceptors 400 rather than declaring a funnel the goal never named.

**Two write acceptors, one mapping, and both are ADDITIVE.** `PUT /orgs/brands/:brandId/current-goal` (now answering `{ funnels }`) and `optimizationGoal` on the economics PUT both call `salesFunnelsService.declareFromRetiredGoal`, so a brand reaches the same declaration whichever way its goal arrived. They switch the named funnels ON and leave every other declaration and every number on it exactly as stored — a goal was one word and the model is multi-funnel, so treating a goal write as "these and only these" would silently switch off a funnel the org stated deliberately. `PUT .../sales-funnels` (the whole-set statement) is the only thing that switches a funnel off.

**The retired columns are still WRITTEN and read by nothing.** `org_brands.current_goal` and its `brand_sales_economics.optimization_goal` mirror are kept so a legacy caller that writes a goal and reads the column back is not lied to, and because the one-time backfill inverted `current_goal` to give every brand carrying a goal the declaration it meant (`scripts/backfill-funnel-declarations.ts` — idempotent on "this pair has no funnel row at all", reversible by `backfilled_from_goal IS NOT NULL`, dry-runnable, and its result read back from an independent query rather than its own log). Do not re-add a read that derives an answer from either column.

**ONE goal-shaped read survives, deliberately: `GET /internal/brands/:brandId/runtime-context` still serves `currentGoal`.** campaign-service's scheduler boots on it for every brand that carries no per-funnel budget, and removing it in this ship would have stopped those brands running — which is the one thing the retirement must not do. It is the last one; read the declared funnel set instead, and do not add another.

**Goal-family rates MUST be NOT NULL with server defaults — a nullable rate breaks the fail-loud consumer.** The form-submission rates shipped nullable in #322, but features-service reads the EFFECTIVE (Gold) layer and fails loud (502) on an absent/null rate, so a nullable rate the effective layer omits = prod-broken for every such brand. They were made NOT NULL with DB defaults `25 / 20`, and the effective layer (`SalesEconomicsAverages` + `getEffectiveByBrandId` user branch + `getAverageAcrossBrands` MEAN + `SalesEconomicsEffectiveResponseSchema`) serves them as real numbers for ALL provenances. **RULE: any conversion rate tied to a funnel must be a NOT NULL column with a server default AND must be carried on the effective serving layer** — never nullable, never omitted from `economics`. Reference: PR #324 (migration 0038); #317/#322/#324/#346 are the goal-set history, and this PR retires it (migration `0054`).

**Downstream, at the time of the switch:** features-service `declared-funnels.ts` read a funnel's `goal` and threw `UnknownFunnelGoalError` without one, and campaign-service's `brand-sales-funnels-client` dropped any funnel with no `goal`. Both migrate to the funnel key; the goal is gone from the payload and is not coming back to unblock them.

## The number to ring when a sales interest lands is BRAND grain, and absence is the answer

`brand_sales_rep_phones` (PK `(org_id, brand_id)`, `phone` text NOT NULL) holds the ONE number to ring when a prospect replies to one of the brand's campaigns saying they are interested — the rep on it is phoned within the minute. Owner: `src/services/salesRepPhoneService.ts`; routes: `src/routes/sales-rep-phone.routes.ts` (GET / PUT / DELETE `/orgs/brands/:brandId/sales-rep-phone`).

**BRAND grain, and campaign grain is the wrong answer even though it looks plausible.** A campaign is (offer x funnel x channel), so storing the number there means retyping one fact once per channel selling the same offer — the brand this was built for already runs four channels on a single offer, four rows drifting from the first edit. A brand with no campaign yet could declare nothing at all, and a newly created campaign would start with no rep and silently place no call. The rep answers for the BRAND.

**Nothing is defaulted, inferred or borrowed.** The user row's phone is the account holder's own number and answers a different question ("who signed up", not "who picks up when a buyer says yes"), and the WhatsApp link is a click destination, not a number to dial. Neither is a fallback here, and there is no platform default. A brand with no row reads `salesRepPhone: null` — a first-class "nobody to ring", never an empty string and never an error, because most brands will never state one.

**Normalised on WRITE, to strict E.164.** The consumer hands the value straight to a telephony provider, so a number that reaches the dialler unusable is a call that never happens, silently — the one failure this must not have. `normalizeSalesRepPhone` accepts whatever format a person typed (spaces, dashes, parens, dots) as long as it carries a country code (`+` or the international `00` prefix, 8-15 digits) and stores `+<digits>`. A national number with no country code is REFUSED 400 rather than completed from the brand's domain, the org, or a default country: a guessed country dials a different person.

**Served on the INTERNAL brand read only.** `salesRepPhone` is on `getBrandDetail` behind `includeSalesRepPhone`, which `GET /internal/brands/:id` and the internal batch read pass and the PUBLIC read (unauthenticated) and the share-token resolve do not — the field is ABSENT there, not null, so neither payload gained per-org contact data. Org scoping on that read: `x-org-id` when the caller sends it, else the number only when a SINGLE org has stated one for the brand (21 production brands are claimed by more than one org, and serving one org's rep to another company's caller is the leak `0050` closed). An ambiguous read answers `null`, not a 400 — absence is already a first-class answer here, so the brand read stays always-200.

**Carried by `rewriteBrandReferences`** like the other user-authored one-row-per-(org, brand) tables — leaving it behind would strand a stated number on an abandoned brand row.

**An offer-scoped override is the anticipated widening** (two offers sold by two different closers, a self-serve one and an enterprise one). It is not built, and nothing here forecloses it: it would be an additive read in FRONT of this one, never a re-key of this table. Migration `0060`. Regression: `tests/unit/salesRepPhone.test.ts`, `tests/integration/salesRepPhone.test.ts`.

## Per-brand CONFIG is keyed on `(org_id, brand_id)` — `brand_id` alone is a cross-org leak

`brands` is the global SILVER identity: one row per normalized domain, deliberately shared. `getOrCreateBrand` hands any org the existing row when the domain already exists and then inserts an `org_brands` membership with **no guard**, and `resolveBrandOwnership` only checks that membership. So keying configuration on `brand_id` alone meant any org could `POST /orgs/brands { url }` with somebody else's domain and read — or overwrite — their private data. This was live: 21 production brands are claimed by more than one org (one by ten), 16 carrying sales economics, 9 confirmed fields.

**Everything a customer configures on top of the identity is per (org, brand).** `brand_sales_economics`, `brand_sales_funnels`, `brand_click_destinations`, `brand_whatsapp_links`, `brand_business_context`, `brand_user_fields`, `brand_share_tokens` all carry `org_id` in their key, and `current_goal` lives on `org_brands` rather than on `brands`. When you add a per-brand config table, key it on `(org_id, brand_id)` — the identity row holds domain, url, name and logo, nothing a customer decides.

**Migration 0047 COPIED rather than attributed.** Every org claiming a brand got its own copy of what it already read, because attributing to one org would have TAKEN the config from the others — 42 (org, brand) pairs and 177 confirmed fields would have vanished from dashboards showing them. Closing a leak does not require deleting anyone's data. Config on a brand no org claims went to `orphaned_brand_config_archive` verbatim before deletion (4 rows; drop the table once reviewed).

**The no-website SHELLS nobody claims go too, and only those.** A no-website brand has no domain, so neither way in reaches it once unclaimed — an org's own brand list (it has no org) or a lookup by domain (it has none) — and it accumulates forever. An unclaimed brand that HAS a domain is the opposite: it is still the global identity row for that domain and the next org to enter it gets that exact row back, so deleting one only has it recreated (16 in production). The delete is additionally guarded on every table that can point at a brand, so a shell carrying anything at all is kept rather than cascaded away, and the row is archived verbatim first. Production had exactly 2, both abandoned duplicates of one business that later onboarded properly with its domain.

**The internal reads resolve the org, they never guess.** `resolveInternalOrgScope` (`src/lib/internal-org-scope.ts`): `x-org-id` when sent; else the single claiming org when there is exactly one; else **400 `ORG_REQUIRED`**. A brand no org claims is not an error — it is "unset", answered with the route's own empty shape (`null`, `[]`), which is the contract those reads always had. Do NOT add a "first claiming org" fallback for the ambiguous case: that reintroduces the leak in the one place it was just closed. Follow-up to make callers send the header: #407.

## A funnel states the event that STARTS it and the step it is NAMED after — and both must resolve

Vocabulary, owner-fixed: the terminal outcome of every funnel is a **SALE** (it is what the customer buys), each intermediate stage is a **STEP**, and the step a funnel is named after is its **MILESTONE**. The word "outcome" is deprecated fleet-wide — it used to mean the retired per-brand optimization goal. Use this vocabulary in anything new.

**`startEvent` is what lets a consumer match a CHANNEL to a funnel**, which is the whole reason it exists now that roughly thirty acquisition channels are opening: a channel that can only produce a phone conversation cannot feed a funnel that starts at a website visit. Three tokens, and they are exhaustive by construction (`SALES_FUNNEL_START_EVENTS`): `conversation_reply` (somebody answered a conversation we started), `website_visit` (somebody landed on the brand's OWN site), `ad_click` (somebody engaged with an ad and stayed on the advertising platform — the brand's site is never touched). `startEvent === 'website_visit'` is exactly `requiresWebsite`, asserted at load.

**`milestoneStep` / `milestoneStepIndex` is what a channel's minimum budget is priced against** — one month must pay for at least one of them — so a consumer READS it instead of hardcoding a funnel-to-step mapping. It is `Meeting booked` for all three meeting chains, `Signup` for `website_purchases`, `Form filled` for `form_magnet`, `Lead form submitted` for `lead_forms_from_ads`, and `Paid client` for `sales_from_conversation` — that last one has no stage before the sale, so the sale genuinely IS the moment it is named after, not a stand-in for a missing step.

**Neither may be defaulted.** `funnelMilestoneStepIndex` throws on a milestone that is not one of the funnel's own steps rather than answering `0`, which is a real position (the starting event). A load-time loop over `SALES_FUNNELS` re-checks the start event, the milestone, the leg count (`legs.length === steps.length - 1`) and the website/start-event agreement, so a catalogue that cannot answer breaks the service at boot — one obvious error — instead of at read time on whichever brand happened to declare it.

**The three chains that begin somewhere else** were added (never renamed over the four, which live brands and live budgets reference): `sales_from_conversation` (Positive reply → Paid client — the sale closes INSIDE the conversation, no meeting ever booked; common under ~$2k and the default where business runs on WhatsApp), `sales_meetings_from_ads` (Ad click → Meeting booked → Meeting attended → Paid client — Meta "Book Now", Google Local Services), `lead_forms_from_ads` (Ad click → Lead form submitted → Paid client — Meta Lead Ads, LinkedIn Lead Gen Forms, TikTok lead forms). The last one is deliberately GENERAL: the same chain prices a webinar signup, a guide download, a quote request and a demo request, so naming it after any one of them would exclude the others. Their four legs (`replyToPaidClientPct`, `adClickToMeetingPct`, `adClickToLeadFormPct`, `leadFormToPaidClientPct`) exist ONLY on `brand_sales_funnels` — `brand_sales_economics` predates these chains and has no column for any of them, so the economics backfill produces no candidate for them and they are stated on the funnel or not at all.

**The terminal step's LABEL stays `Paid client` on every chain, old and new.** The four original chains have carried it since before this vocabulary was fixed and live consumers render it; a new chain spelling the same stage differently would describe one model as two. Migration `0056` WIDENS the `funnel_key` CHECK (drop + re-add — Postgres has no ALTER CONSTRAINT for a CHECK expression) and adds the four nullable rate columns. Regression: `tests/unit/funnelStartEventAndMilestone.test.ts`, `tests/integration/funnelsBeyondConversationAndWebsite.test.ts`.

## A rate belongs to an ARROW, named by the two steps it connects — the named rates stay, and the stated arrow wins

`brand_sales_funnel_arrow_rates` (unique on `(offer_id, funnel_key, from_step, to_step)`, `rate_pct` NOT NULL) holds the rate a brand states for ONE arrow of one funnel. Owner: `src/services/salesFunnelArrowRatesService.ts`; the catalogue side is `funnelArrows` in `salesFunnelCatalogue.ts`.

**Why it is a row and not a column.** The rates on `brand_sales_funnels` are a CLOSED set — one column per arrow the original funnels happened to contain, so the set IS a schema. Funnels are gaining steps (a phone call placed between a positive reply and a booked meeting is the first, and there will be more), and under the named-column model each one costs a migration here plus a rename wave through brand-service, features-service and the dashboard. That cost is what blocked the change, not the product decision. Keyed on the two step LABELS, a brand prices an arrow this service has never heard of and nothing downstream learns a new field name.

**Deliberately NOT validated against the funnel's steps.** An arrow whose steps are not in today's catalogue is accepted and stored — that is the point. `assertArrowIdentifiable` refuses only shapes that could never name an arrow (an empty label, a step pointing at itself). Do not add a CHECK on the step columns and do not reject an unknown arrow: the next funnel to gain a step must not need a deploy here first.

**ONE precedence, and it is the only one: the STATED ARROW WINS, the legacy named rate is the FALLBACK.** `resolveFunnelArrowRates` walks the funnel's own arrows in funnel order and answers each with the stated rate if there is one (`provenance: 'stated_arrow'`), else the named column covering it (`'named_rate'`), else `null` (`'unstated'` — never a zero, never a neighbouring arrow's number). Arrows the brand stated that the catalogue does not name come after, with `rateKey: null`. **`rates` itself is untouched by all of it** — it still carries exactly the named legs of the funnel and still answers the same numbers, so no current consumer changes and a brand that has stated no arrow reads identically to before. That is what let this ship alone.

**The named rates are NOT removed.** A later, separate ship retires them once every consumer has moved. Until then both vocabularies are live, they reconcile only through the precedence above, and there is no read that derives a named rate from an arrow (or the reverse) — the arrow view is a projection, the columns are the store.

**Writes ride the existing funnel PUT** (`arrowRates: [{fromStep, toStep, ratePct}]` on `PUT /orgs/brands/:brandId/sales-funnels/:funnelKey` and its offer-scoped sibling), partial like every other field: an arrow the patch omits is left as stored, and an explicit `null` DELETES the row rather than storing a null — which is what keeps "not stated" a single state. Erasing a funnel (`?erase=true`) takes its arrow rates with it, and `rewriteBrandReferences` carries them like the funnel rows themselves. Regression: `tests/unit/funnelArrowRates.test.ts`, `tests/integration/funnelArrowRates.test.ts`. Migration `0059`.

## Sales FUNNELS — `active` is the memory, and the last one cannot be switched off

A funnel row is never deleted on the normal path. Switching one OFF keeps its rates, its lifetime revenue and its destinations, so switching it back on returns what the user entered instead of an empty form — that is the whole reason `active` exists rather than a DELETE.

**An org that has answered always keeps at least one ACTIVE funnel.** Switching off the last one, or stating an empty set, is refused (`LastActiveSalesFunnelError` → 400). That makes "answered, but sells through nothing" unreachable, which is what leaves **zero rows as the only way to say "never answered"** — and is why there is no separate declaration marker table. Do not add one back.

The ORG read returns active and inactive funnels alike (the screen needs the numbers it is holding); the INTERNAL read returns **only the active ones**, because a scheduler asking what an org sells through must never rank a funnel it switched off.

**The list is the whole answer — there is no `declared` flag.** One existed, saying exactly what a non-empty list says, and it was briefly re-served after the org-scoping ship purely because features-service refused a payload without it. features-service reads the list alone as of v0.118.0 and the flag is gone (migration `0052` also dropped `orphaned_brand_config_archive`, the reviewed 0050 archive). Do not reintroduce a second way to say "this org has answered": absence of rows is the only one.

**Erasing is a SEPARATE, OPT-IN act — `DELETE ...?erase=true`.** Retiring stopped destroying data, so there had to stay a way to actually destroy it; making it a flag on the same route is what keeps the ordinary deselect non-destructive while leaving a deliberate "forget what I told you" reachable. `eraseByBrandId` deletes the row outright and is refused (400, the same `LastActiveSalesFunnelError`) when it would leave the org holding funnel rows with NONE active — erasure must not reach the state deactivation cannot. Erasing the LAST remaining row IS allowed: it returns the brand to zero rows, which is exactly "never answered". An `erase` value that is neither `true` nor `false` is a 400, never read as "no" — a mistyped destructive flag must not silently get the other behaviour.

## What a brand priced BEFORE the funnel model is MOVED onto its funnels, once — never defaulted on read

The goal→funnel backfill gave every brand carrying a retired goal the declaration that goal meant, carrying the funnel key and its provenance and **not one number**. The rates and the lifetime revenue those brands had entered sat untouched on `brand_sales_economics` — the BRAND-WIDE record the funnel model replaced — so Settings rendered every field empty on a funnel the customer had already priced. `scripts/backfill-funnel-economics.ts` moves them across, once.

**Same name, same number, nothing else.** `ratesForFunnel` (`src/lib/funnel-economics-backfill-plan.ts`) fills a leg of the funnel's OWN chain from the economics column that shares its name, and writes nothing else — the catalogue owns the chains, so which legs a funnel has is never guessed. `meetingBookedToAttendedPct` exists only on the funnel table and was never stated anywhere, so it stays NULL rather than being invented; a leg is never borrowed from another chain (the website meeting funnel never takes `replyToMeetingPct`). A brand that stated nothing has no economics row, so the INNER JOIN never produces a candidate and absent stays absent.

**Only an UNPRICED declaration is touched**, and the "every value column IS NULL" predicate is repeated in the UPDATE so a row priced between the read and the write is left as the user left it. A funnel a human priced is never edited — **not even on a column they left empty**: half-filling it from a brand-wide record would put a number they did not enter beside the ones they did.

**Who DECLARED the funnel is not a rule, and requiring it hid the brands that needed this most.** The first run also demanded `backfilled_from_goal IS NOT NULL`, so it only ever saw declarations the goal→funnel backfill had made. That was invisible while the brand-wide record still PRICED a brand whose funnels held nothing — the numbers were reachable either way. It stopped being invisible when a brand's rates and lifetime revenue became the FUNNEL's (features-service prices its pipeline on the declared funnel, and the brand-wide record is now a legacy fallthrough and a prefill): a funnel somebody declared BY HAND and left blank then loses the numbers its brand had stated, silently, and reprices to nothing. So the predicate is unpriced-ness alone. Nothing else widened — a brand that stated nothing still has no economics row and so no candidate, and a funnel carrying any value is still untouched.

**This is a one-time MIGRATION of stated data, NOT a defaulting layer.** Do not add a read-time fallback that seeds a funnel's missing rate from `brand_sales_economics`: a value that was never written must keep reading as absent, so a consumer knows not to rank on it. Reversible by exact predicate on `economics_backfilled_at` (migration `0055`), idempotent, dry-runnable. Applied 2026-08-06: 109 rows across 64 brands.

**The "duplicate declarations" are per-ORG rows on a brand several orgs claim, and they are correct.** The table's primary key is `(org_id, brand_id, funnel_key)`, so one org can never hold two declarations of one funnel — a second insert is rejected, not appended. What production shows is 200 rows over 142 distinct `(brand, funnel)` pairs because 21 brands are claimed by more than one org (one by ten), and migration `0050` deliberately COPIED each org its own config rather than attributing a shared brand to one of them. Every read is org-scoped, so each org sees each funnel exactly once. Do NOT "dedupe" to one row per `(brand, funnel)`: that deletes other orgs' declarations, which is the leak `0050` closed being reopened as data loss.

## A brand claimed by ten orgs is ten rows and ONE data point — every fleet-wide aggregate collapses per brand first

The same thing is true of `brand_sales_economics`, keyed on `(org_id, brand_id)`: production carries 112 rows over 70 brands (54 brands at one org, one at nine, one at ten), and every row is a legitimate per-org copy that `0050` created rather than take one org's config from the others. Both composite primary keys are live in production, so **the natural key is already enforced and a re-run of either write path converges** — `declareFunnels`/`upsertByBrandId` are `ON CONFLICT` upserts on the full key, and both one-time backfills are additionally guarded on their own provenance column. There is nothing to de-duplicate, and no uniqueness constraint to add. Counting distinct `(brand, funnel)` or distinct `brand_id` is counting the pre-`0050` key.

**What the copies DO break is any aggregate that spans the whole table without grouping.** `getAverageAcrossBrands` — the fleet benchmark served with provenance `cross-brand-average` to every (org, brand) pair that has priced nothing, 77 of them today — averaged the raw rows, so a brand ten orgs claim was ten data points and a brand one org claims was one. That is not a de-duplication question: the rows must stay, but a benchmark weighted by claim count is not the number it says it is. It now aggregates over a per-brand collapse (the mean of that brand's org copies — they can legitimately diverge once each org edits its own), which is one brand, one data point. The LTV median stays a `ROUND(PERCENTILE_CONT(...))` over `double precision` so its half-to-even rounding is unchanged.

**When you add a fleet-wide read over any per-`(org, brand)` config table, GROUP BY the brand first.** The per-brand and per-row answers agree only while every brand is singly claimed, so the bug is invisible in a fixture and invisible in the code. Regression: `tests/integration/crossBrandAverageWeighting.test.ts` (five orgs claiming one brand move the benchmark by one brand's worth, and it asserts the two answers genuinely differ on its fixture so it cannot pass with the collapse removed).

## Six offers named "Press Coverage" on one brand are SIX ORGS, not six clones — do not merge them

`brand_offers` is per-`(org, brand)` like every other table a customer configures, and the one-time migration created exactly ONE offer per pair. Production carries **188 rows over 188 distinct `(org_id, brand_id)` pairs and 139 brands** — verified: `count(*) = count(DISTINCT (org_id, brand_id)) = 188`, so **no org holds two offers for one brand anywhere on the platform**. The 21 brands showing several rows are the 21 brands claimed by several orgs, one by ten. Rows created half a second apart are one pass of one loop over those pairs, one LLM naming call each, which is what the loop is.

Read as a flat table they look exactly like clones of one proposition, and the repair that suggests itself — merge onto a survivor, repoint the campaigns — **deletes nine orgs' configuration and hands their campaigns to a tenth org's row.** That is the leak migration `0050` closed, reopened as data loss. The same trap as the "duplicate declarations" on `brand_sales_funnels` above: the key you are counting against is the pre-`0050` one.

**No campaign is split across those rows.** `campaign_service.campaigns.offer_id` was populated per org, and it holds: of 700 campaigns, 555 carry an offer, referencing 45 offers, and **every one of the 45 belongs to the org that owns the campaign — zero org mismatches, zero dangling ids.** A brand whose campaigns look "split 53 / 6 / 1 across three clones" is three ORGS running their own outreach on a domain they each claim, and each of them sees one row carrying all 53, or all 6, or the 1. Verify the same way before believing otherwise: join `campaigns(offer_id, org_id)` to `brand_offers(id, org_id)` and count the mismatches, rather than reading offer names off a listing.

**A name that differs between two of those rows — "Electric Cars" / "Electric Vehicles", "Co-working" / "Coworking" — is two orgs' independent naming calls on one brand, not a bad merge key.** Each org sees only its own, so nothing incoherent is rendered; and the offer name is a label a person can rename at any time through `PATCH .../offers/{offerId}`.

**Every read, write and resolution is org-scoped, and that is what must not regress.** `listOffers`, `getOffer` and therefore `resolveSoleOffer` all filter on `org_id`, so a brand ten orgs claim still resolves to ONE offer per org and a brand-scoped call never 409s `SeveralOffersError` on somebody else's row. `getOfferById` (internal, offer id alone) reads the org OFF the row rather than taking one. Regression: `tests/integration/offersAcrossOrgsClaimingOneBrand.test.ts` (three orgs on one brand, same offer name, independent prices, `404` across orgs, `ORG_REQUIRED` on the org-less internal read), plus `tests/unit/offerMigrationPlan.test.ts` for the per-pair planning and the empty re-run.

## Every reader of the confirmed fields names an OFFER — there is no brand-scoped read of them left

The 7 user-facing fields are ONE proposition's words, so "the brand's confirmed fields" is not a question with an answer once a brand sells two things. `getConfirmedByBrandId` was the compatibility wrapper that resolved the sole offer and it is GONE; the only read is `getConfirmedByOfferId(orgId, brandId, offerId)`, and every caller states which offer it means through **`resolveNamedOffer(orgId, brandId, offerId?)`** (`brandOffersService`):

- **an offer NAMED** → proved to exist under this `(org, brand)` with `assertOfferOnBrand`, else `OfferNotFoundError` (404). Naming another brand's offer is never a quiet fall back to this brand's rows.
- **nothing named** → `resolveSoleOffer`'s three answers unchanged: the sole offer, `null` for a brand with none, and the deliberate `SeveralOffersError` (409) for a brand selling several.

**A wrong pick here is worse than the 409**, which is why no default was added. The confirmed words are used TWICE on the extraction path — injected into the prompt as authoritative context and overlaid back over the model's answer — so grounding a $200 self-serve extraction in a $20k enterprise promise produces output that reads perfectly and is wrong throughout. Both halves resolve from the SAME `offerId` (`extractFields` for the prompt, the overlay loop in `multiBrandFieldExtractionService`), so they can never disagree.

**What each caller can name, and it is not the same answer:**

- `POST /orgs|internal/brands/extract-fields` — optional body `offerId`, **single-brand requests only**. An offer belongs to one brand, so one id cannot name a proposition on each of several: `OfferIdWithSeveralBrandsError` (400) rather than an id applied to one brand and ignored on the rest.
- `POST /orgs/brands/:brandId/icp/suggest` — optional body `offerId`. Who to prospect follows from what is being sold, so a brand selling two things has two ICPs.
- `GET /internal/brands/:brandId/runtime-context` — optional `?offerId=`. campaign-service holds the campaign and a campaign belongs to an offer, so the CALLER is the one that can name it. Until it sends the param, a multi-offer brand answers 409 there — deliberately, and loudly.

Every one of these is ADDITIVE: omitted, the read is byte-for-byte what it was, which is the whole of production (every brand holds exactly one offer). The brand-scoped user-fields and sales-funnel ROUTES are untouched — their 409 is the answer for a caller that names nothing, not a gap. `rejectOfferProblem` maps both failures at each route, so an unresolvable offer surfaces as 404/409 instead of a 500. Regression: `tests/integration/internalReadersOfferGrain.test.ts`, `tests/unit/extractionOfferGrain.test.ts`.

## Boot: the port binds BEFORE migrations, and a gate — not a wait — is what protects the schema

`src/index.ts` calls `app.listen()` FIRST and runs `migrate()` behind it. Do NOT restore the old `migrate().then(listen)` order, and do NOT reintroduce `process.exit(1)` on migration failure.

**Why.** Neon computes suspend after inactivity and take seconds to resume. Awaiting `migrate()` before `app.listen()` means a deploy landing on a cold compute spends its entire startup budget on the first connection: the port never opens inside Railway's ~30s healthcheck window, the deploy is marked FAILED, and the container produces **no application output at all** — not even "Migrations complete" — because it stalled before any logging. The failure has nothing to do with the code being deployed, which is what makes it expensive: it reads as a flaky deploy, you retry onto a now-warm compute, it passes, and the cause is never found. Reproduced on a cold compute 2026-07-30; keeping the compute awake with a `SELECT 1` for the duration of the deploy made the identical deploy pass unchanged. Production runs `suspend_timeout_seconds: -1` so it does not hit this; the staging branch (`br-late-bar-azf3okfj` / `ep-muddy-shadow-az2cm0t6`) runs 300s and hits it after any idle period.

**Binding first does NOT mean serving early.** `app.use(requireMigrationsReady)` sits above every router and below `/`, `/health`, `/openapi.json` (the three that need no database). Until the migrator finishes, every database-backed route answers **503 `MIGRATIONS_PENDING`** with `Retry-After: 5`. The service refuses rather than answering against a schema it has not verified — the guarantee the old `await` gave is kept, just enforced per-request instead of by blocking the port.

**Retry only the connect phase.** `runMigrationsWithConnectRetry` (`src/lib/boot-migrations.ts`) retries on `ETIMEDOUT` / `ECONNREFUSED` / `CONNECT_TIMEOUT` / postgres.js's pool-acquire `"timeout exceeded when trying to connect"` / `"the database system is starting up"`, walking `err.cause` and `AggregateError.errors` (happy-eyeballs emits one sub-error per resolved address). Backoff `250 → 8000`, ~31s total, none of it on the healthcheck's critical path. A statement-level error (bad SQL, failed constraint, `42P01`) is **never** retried — it is a real migration failure.

**Failure is louder than an exit, not quieter.** On a real failure: the error is logged in full, state flips to `failed`, every database route answers 503 `MIGRATIONS_FAILED` with the detail, and `/health` itself returns **503** so Railway marks the deploy unhealthy and keeps the previous container serving. The process deliberately stays alive: `process.exit(1)` crash-looped against `railway.json`'s `ON_FAILURE` / 10 retries and took the port down with it, so nothing could report why.

`NODE_ENV === 'test'` marks migrations ready at import so the exported app is usable; the integration harness (`tests/helpers/test-app.ts`) builds its own app and has no gate. Regression: `tests/unit/bootMigrations.test.ts`, `tests/integration/migrationGate.test.ts`. Issue: #386. Note #386's own "Fix" section proposes `connect_timeout` + `idle_timeout` postgres.js options — PR #389 disproved both (`connect_timeout: 30` is already the postgres.js default; `idle_timeout` defaults to `null` on postgres.js, so setting it makes idle connections close and costs a fresh TCP+TLS handshake — that advice is node-postgres's, mis-transplanted). Do not re-add either.

## LLM cost declaration — the gate lives with WHOEVER performs the terminal LLM call

brand-service does NOT hand-write `provisioned`/`actual`/`cancelled` cost rows for LLM spend. WHERE the affordability gate + cost declaration live depends on HOW the route reaches the LLM. Two distinct patterns — do NOT conflate them, and do NOT add a redundant pre-authorize to the chat-delegated one:

**Pattern A — LLM via chat-service `chat()` (the DEFAULT for org routes). NO pre-authorize in brand-service.** When the route reaches the model through `chat()` (`src/lib/chat-client.ts`) in **org mode** (`OrgCaller`), chat-service `POST /complete` is the terminal caller, so IT already gates affordability (returns **402 "Insufficient credits"** when the org can't pay) AND declares the real token cost on the child run. A brand-service `authorizeCredits()` call here is **redundant** and actively harmful — it duplicates the gate and (because the cost name is hand-written) can 502 on a name the costs catalog doesn't have. So the canonical chat-delegated org route = `createRun` (child run) → `chat(orgCaller-with-run.id)` → `updateRun completed/failed`, and **propagate chat-service's 402** (a thrown `...returned 402` from `fetchWithRetry` must re-emit as 402, not 500). Forward a brand-service run id as `x-run-id` so the chat run nests. Reference: `src/services/personaSuggestionService.ts`, `src/services/fieldExtractionService.ts`. `chat()` in **platform mode** hits `/internal/platform-complete` — NO billing, NO run tracking; org-less internal calls only. (Set 2026-06-16, #241 dropped the redundant persona-suggest pre-authorize that #232 wrongly added; #232's guessed cost name had already 502'd against costs-service.)

**Pattern B — RAW LLM SDK in-process (e.g. `analyze.routes` → `geminiAnalysisService` via `@google/generative-ai`). brand-service `authorizeCredits()` IS the gate.** When the route calls the provider SDK directly (no chat-service hop), brand-service's pre-authorize is the ONLY affordability gate, so it stays. Rules for it: `!sufficient` → 402; billing throw → 502 (fail loud, never swallow). **Cost name MUST be byte-equal to a costs-service catalog row — verify against `costs GET /v1/platform-prices`, NEVER hand-guess.** The catalog uses the `google-flash-2.5-tokens-input`/`-output` form (provider-first) — NOT `gemini-2.5-flash-tokens-*`, which does not exist → billing 502 "Failed to resolve prices from costs-service". (#232 copied the wrong `gemini-*` form into both analyze + personas; fixed to `google-flash-2.5-tokens-*` for analyze, removed entirely for personas.)

**Billing endpoint (Pattern B):** `authorizeCredits()` (`src/lib/billing-client.ts`) hits **`POST /v1/customer_balance/authorize`** — NOT `/v1/credits/authorize` (that route does NOT exist → 404). Body `{ items:[{costName,quantity}], description? }`; response `{ sufficient, balance_cents, required_cents }` where the two cents fields are **decimal STRINGS**. Verify the path against the deployed billing openapi via api-registry; the `billingClient` unit test MUST assert the deployed path (a test that codifies the wrong path let the 404 ship green in #232 → hotfix #236). (Set 2026-06-16, #232 personas-suggest 404 → hotfixes #236/#241/analyze cost-name.)

### A destructive DROP of a user-data table MUST backfill into its replacement BEFORE the drop — in the SAME migration

When a migration `DROP`s a table that holds **user-authored / confirmed** data (offer fields, sales economics, thesis, confirmed profile values — anything a user validated in the dashboard, not an ephemeral extract cache), the same migration MUST first `INSERT INTO <replacement> SELECT ... FROM <dropped_table>` (mapping renamed keys). Creating the replacement EMPTY and dropping the old table in one PR with NO backfill is silent user-data loss — the read path then falls through to the ephemeral "suggested" layer and every confirmed field renders as amber "AI-suggested". Recovery is only possible inside the Neon PITR retention window (24h) via a point-in-time branch; past that, the data is gone forever.

### A HOTFIX migration is numbered against every branch that exists, and its snapshot must be rebased onto staging's before the sync merges

Two separate traps, both invisible locally, both hit by hotfix v0.60.1 (`0048_brand_share_token_org`, #408).

**Numbering.** The workspace branch is cut from `origin/main`, so the local journal lags staging. `git show origin/staging:drizzle/meta/_journal.json | tail` is necessary but NOT sufficient: a SIBLING CONDUCTOR WORKTREE routinely holds an unpushed migration at the next free number, and nothing on the remote shows it. Check the worktrees too — `ls ~/conductor/workspaces/brand-service/*/drizzle/*.sql | tail` — and take the first number nobody is using. A GAP is fine (the runtime migrator walks the journal in array order; `idx` is informational), a duplicate `NNNN_` prefix is a merge conflict. v0.60.1 skipped to 0048 because staging held 0046 and the `org-scoped-brand-config` worktree held an unpushed 0047.

**Snapshot rebase.** `drizzle-kit generate` on a main-based branch writes a snapshot describing MAIN's schema plus your change — so it does not contain the tables staging added meanwhile. The `.sql` is correct and the hotfix ships fine, but once the sync lands, the next `drizzle-kit generate` on staging diffs `schema.ts` against your snapshot and emits **staging's own tables again as phantom drift** — and whoever hits it has no reason to suspect the snapshot. Fix it ON THE SYNC BRANCH, after resolving the journal (keep BOTH entries, in order): delete your `<n>_snapshot.json`, drop its journal entry, re-run `drizzle-kit generate` (it now diffs against staging's latest snapshot), then **keep only the regenerated snapshot** — rename it to `<n>_snapshot.json`, delete the throwaway `.sql` it emitted, and restore your resolved journal. The regenerated `.sql` is the proof: it must contain ONLY your change (v0.60.1's was the single `ADD COLUMN "org_id"`), which is what confirms no other delta got folded in. Then `drizzle-kit generate` must report **"No schema changes, nothing to migrate"**. The already-applied `<n>_*.sql` is untouched, so the runtime ledger (which hashes the SQL, not the snapshot) never notices.

**The same snapshot rebase is due whenever ANY sibling migration lands while your migration branch is in flight — not only on a hotfix.** Merging `origin/staging` gives you their `.sql` and their snapshot, but YOUR snapshot still describes the baseline you branched from, so the next `drizzle-kit generate` re-emits their tables as phantom drift. Same fix, on the merge commit: delete your `<n>_snapshot.json`, drop its journal entry, re-run `drizzle-kit generate`, rename the regenerated snapshot back to `<n>_snapshot.json`, delete the throwaway `.sql` and restore the journal entry. The throwaway `.sql` is the proof — it must contain ONLY your own change. And **re-read the sibling's migration before trusting your own**: if it MOVED the column you are migrating (#423 moved the goal from `brands.current_goal` to `org_brands.current_goal` mid-flight), your migration now targets a column that no longer exists and the merge resolution has to retarget it, not just renumber it.

### A hotfix migration authored on `main` STRANDS every unpromoted staging migration in production — forever, and silently

The runtime migrator applies only migrations stamped ABOVE the last one it recorded. So the moment a hotfix authors a migration on `main` and production applies it, **every migration sitting unpromoted on `staging` with an earlier stamp becomes permanently unreachable in production**: the later promote inserts it into the middle of the journal, below a bar production has already cleared, and it never runs. Staging is fine — it applied them in order — so the two environments diverge with no error anywhere.

It is silent by construction. The journal stays perfectly sorted, `tests/unit/migration-order.test.ts` passes, CI is green (it builds a fresh branch from `schema.ts` and never replays the journal), and the promote succeeds. Nothing reports a pending migration, because from the migrator's point of view there isn't one. The only place the hole exists is production's `drizzle.__drizzle_migrations` ledger, and the only symptom is a `42P01` at runtime on whatever the missing table was — which surfaces on whichever route touches it first, not on deploy.

**Before authoring a migration on a hotfix branch cut from `main`, check whether `staging` holds migrations `main` lacks** — `git show origin/staging:drizzle/meta/_journal.json` against `origin/main`'s. If it does, that hotfix migration will strand them. Either promote first, or accept it and re-create the stranded ones afterwards.

**The repair is a NEW migration, never an edit.** Re-stamping or renumbering the stranded file changes the hash the ledger stores, so environments that DID apply it re-run or error. Copy its statements verbatim into a fresh migration numbered off `main`'s journal tail with a stamp above the last applied one, and rely on the `IF NOT EXISTS` idempotency to no-op where it already ran. Verify against production's ledger directly (`SELECT created_at FROM drizzle.__drizzle_migrations ORDER BY created_at DESC LIMIT 1`) — a stamp is only "high enough" relative to what production actually recorded, not to what the journal says.

### A test that re-implements a DB aggregate must mirror Postgres rounding (`ROUND(double precision)` = half-to-even), and a NEW integration test file can deterministically expose latent cross-file fragility

Two compounding gotchas, observed 2026-06-18 (#272 added `internalPersonas.test.ts`, turned `salesEconomicsEffective.test.ts` red on CI only):

1. **Rounding convention.** `salesEconomicsService.getAverageAcrossBrands` rounds the cross-brand median in SQL: `ROUND(PERCENTILE_CONT(0.5) … )::int`. `PERCENTILE_CONT` returns `double precision`, and Postgres `ROUND(double precision)` rounds **HALF-TO-EVEN** (banker's) — `2462.5 → 2462`. JS `Math.round` rounds **half-UP** — `2462.5 → 2463`. A test that recomputes the expected aggregate in JS must mirror the SQL rounding (use a `roundHalfToEven` helper), or the byte-equality assertion diverges by 1 whenever the value lands on a `.5` tie. This is NOT a product bug — the SQL value is correct.

2. **Schedule perturbation.** The cross-brand-average test asserts over the GLOBAL `brand_sales_economics` set (by design). Adding ANY new integration test file changes vitest's deterministic file-parallelism schedule, which changes which concurrent rows are live during the assertion window — so a previously-hidden `.5`-tie (or any global-aggregate fragility) can flip to a hard, repeatable failure in a PR that never touched the aggregate or its service. When a global-aggregate test fails ONLY on your branch and your diff doesn't touch that table/service, suspect schedule-perturbation exposing a latent test defect (rounding, tie, non-isolation) — fix the test to be robust; do not chase it as a product regression.

### No-website brands: pasted business context is the alternative extraction SOURCE

A brand can be created with NO website. `brands.url` and `brands.domain` are NULLABLE (migration `0043`); a no-website brand is created via `POST /orgs/brands { name }` (user-provided display name — the identity, since there's no domain to derive one) and has `url = domain = null`, no domain dedup (each `{ name }` create is a distinct row — two nameless-domain businesses are genuinely distinct). Its field-extraction source is a per-brand free-form text row in **`brand_business_context`** (`content` up to ~1MB, durable/no-TTL), written via `PUT /orgs/brands/:brandId/business-context` (the app raises the JSON body cap to `2mb` for it).

**The source switch lives in `fieldExtractionService.extractFields`:** if `brand.url` is set → scrape+extract exactly as before (unchanged); if `brand.url` is null → read `getBrandBusinessContext(brandId)` and extract from that text (chunked into ≤100k-char "pages" via `chunkBusinessContext` so nothing is sliced by `extractFieldsFromContent`'s per-page cap), skipping map/scrape entirely; if a brand has NEITHER a url NOR business context → **fail loud** (throws `neither a website URL nor pasted business context`), never a fabricated/empty result. `extractFields` reads `brand.url` FRESH on every call, so the **auto-switch when a website is added later rides the EXISTING extraction cache TTL** — once `PATCH /orgs/brands/:brandId { url }` sets the url, the next post-cache-expiry extraction re-sources from the site with NO new cron/TTL. `multiBrandExtractFields` no longer rejects a null-url brand (it delegates the source decision to `extractFields`) and keys its `byBrand`/`byDomain` maps on `brand.domain ?? brandId` (no-website brands have no domain). Consumers of `BrandDetail` (GET `/internal|public/brands/:id`) must handle nullable `url`/`domain`/`logoUrl`/`clickDestinationUrl` — a no-website brand has null for all four; `name` is always non-null. Regression pattern: `tests/unit/noWebsiteExtraction.test.ts`, `tests/integration/businessContext.test.ts`. Reference: PR (this branch).

### Brand name is an INDEX-FIRST priority chain resolved at CREATE (no LLM / Firecrawl / run / cost)

`brands.name` is derived by ONE chain, in this order — each link falls through to the next, the last one can never fail:

1. **logo.dev Search API** (`src/lib/logo-dev-search.ts`, `searchBrandNameByDomain`) — the authoritative company index. `GET https://api.logo.dev/search?q=<domain-or-label>&strategy=match&is_profane=false`, `Authorization: Bearer <secret>`, 3s timeout. Metered on the monthly REQUEST pool (not the Brand-API credit grant), so it is safe per create. **Match discipline: the endpoint is name-to-domain and returns up to 10 fuzzy candidates, so a hit counts ONLY when its `domain` equals the brand's own domain** (www/case-normalized) — a name match on a different domain is rejected, never used. Queries the full domain first, retries once on the bare label. The key is the platform provider **`logo-dev-secret`** (the `sk_...` SECRET key) — NOT `logo-dev`, which holds the PUBLISHABLE `pk_...` token used to build `img.logo.dev` image URLs and does NOT authenticate Search. Every failure here (key not registered, network, non-2xx, non-array body, no domain match) logs loudly and returns `null` so link 2 runs — an explicit fall-through with a guaranteed terminal fallback, not a swallowed error. A missing key must never fail a brand create.
2. **Landing page HTML** — `fetch` of the landing URL (browser User-Agent, 5s timeout), parsed by `parseBrandNameFromHtml`: `og:site_name` → `<title>` (site-suffix trimmed) → JSON-LD `Organization`/`WebSite` `.name`.
3. **Titlecased domain** (`titlecaseDomain`) — guaranteed non-empty terminal fallback.

**The chain runs at CREATE, not on read.** `getOrCreateBrand` → `fillBrandNameOnCreate` awaits ONLY link 1, so `POST /orgs/brands` returns a real `name` (never null) without ever waiting on a fetch of the customer's own website. On an index miss it persists the titlecased domain immediately and fires `upgradeProvisionalBrandName` in the BACKGROUND (link 2), whose UPDATE is conditioned on `name = <that exact placeholder>` — so a real name (user-set, or another writer's) is never clobbered. `persistBrandNameIfAbsent` writes only `WHERE name IS NULL` and returns whatever the row ends up holding, so **a stored name is never re-derived or overwritten**.

`ensureBrandName()` remains the read-path safety net (`GET /internal/brands/:id` etc.) for rows created before this — it runs the same chain and keeps `name` non-null on brand-detail reads. The `NODE_ENV === 'test'` bypass skips ALL network (index + landing fetch): the read path persists the raw domain, the create path persists the titlecased domain.

Regression: `tests/unit/logoDevSearch.test.ts` (match discipline, key absent, transport failures), `tests/unit/brandNameIndex.test.ts` (chain order on both paths, background upgrade, no-overwrite), `tests/integration/ensureBrandName.test.ts`.

Concurrency on the read path is still coordinated: multiple null-name reads share one in-process singleflight `Map<brandId, Promise<string>>` (`inFlightBrandNameFills`); Railway runs one instance, so this is acceptable — replace with a DB/advisory lock if brand-service becomes multi-instance. Always re-read `brands.name` after entering the fill gate before fetching.

**Field extraction** (`fieldExtractionService.extractFields`, the services / full-profile path — distinct from name-fill) selects its model by `urlStrategy`: `landing` → `flash-pro` (Gemini 3.5 Flash) + `disableThinking: true` (floors Gemini 3 thinking to "minimal" = cheap + fast; the single-page "sellable services vs internal steps" discrimination needs judgment `flash` was too weak for — do NOT remove `disableThinking`, that defaults Gemini 3.5 Flash to HIGH thinking); `url_map` → `pro`, chat-service default bounded thinking (deep multi-page background profile). **Scraped page content is capped at 100k chars/page (≈25k tokens) with NO global combined-content cap** — page counts are bounded (`landing` = 1, `url_map` ≤ 10 → worst case ~1M chars, fits Gemini's context); the prior 15k/page cut sliced services listed lower on long landing/pricing pages. (Set 2026-07-09, #329.) **Both paths send a strict `responseSchema` built by `buildFieldsResponseSchema(keys)`** — a Gemini-compatible object schema (every key `required`, each value `anyOf:[string, array<string>]`, deliberately NO `additionalProperties:false` which Gemini 400s on). This is load-bearing: without it the url_map 19-field extraction sent free-form JSON, Gemini 3 Pro flaked and emitted malformed/truncated JSON mid-output, and chat-service strict-parsed it to a **502 "Model returned malformed or truncated JSON"** (a char position well under the token cap = genuine model malformation, NOT a MAX_TOKENS truncation). The sibling `multiBrandFieldExtractionService.consolidateFields` carries the same schema. `thinkingBudget` is DEAD on the /complete path — chat-service only honors `disableThinking`; never re-add a `thinkingBudget` param to a `chat()` call. (Set 2026-06-29, v0.43.1 #306.) Its URL selection has three distinct states:
- `{"urls":[]}` is valid: the LLM found no relevant pages. Store `Unknown` with `sourceUrls: []` and do not scrape.
- Malformed URL-selection output is a backend error. Do not silently fall back to homepage/first 10 URLs.
- URLs selected but 0 usable page content is a scraping failure. Throw a diagnostic error with selected/cached/fresh/empty counts and the affected URLs.

Observed 2026-06-09 (new brand `luxvillageseminyak.com`): parallel name-fill runs (then LLM-based) caused one `/internal/brands/:id` request to 500 with opaque `Failed to scrape any pages`. The deterministic fill removes that failure mode for names entirely.

**`extract-fields` has TWO behaviors via the optional `mode` body param (`ExtractFieldsRequestSchema.mode: 'extract'|'suggest'`, default/omitted = `extract`), honored on BOTH `/orgs` and `/internal` routes.** `extract` = today's site-grounded extraction, returns `"Unknown"`/`["Unknown"]` when the info is absent (BYTE-IDENTICAL to pre-mode — the extract-branch prompt is untouched). `suggest` = the prompt flips to an Alex-Hormozi + top-3-industry-expert generative persona (`extractFieldsFromContent` branches on `mode`) that writes a best-effort value for EVERY field, inferring from the business where the source is silent, and NEVER returns `"Unknown"`/empty — while forbidding fabricated absurd/false/unverifiable specifics (invented numbers, named customers, guarantees). Both modes keep `temperature:0`, the same `responseSchema`, the same model-by-`urlStrategy` selection, and the same date/urgency guard. **Cache isolation is by SALTED hash: `hashFieldDescription(description, mode)` — `extract` hashes the raw description (byte-identical key → every existing `brand_extracted_fields` slot stays valid, no re-extraction churn on deploy), `suggest` salts the input → a disjoint hash space, so a suggest value is NEVER served to an extract request or vice-versa.** `mode` threads: schemas.ts → both routes → `multiBrandExtractFields` → `extractFields` (`getCachedFields`/`upsertExtractedFields`/`extractFieldsFromContent`) + the cross-brand `consolidateFields` prompt + `buildConsolidatedCacheKey`. In `suggest` mode the `selectedUrls.length === 0` "store Unknown" shortcut is bypassed (falls back to the landing page) so the never-Unknown contract holds. Regression: `tests/unit/extractionSuggestMode.test.ts`. Reference: PR (this branch).

## "Write it again from my website" needs the confirmed value withheld in BOTH places, and only for the keys asked for

A caller can ask to REGENERATE a confirmed field — `regenerateFieldKeys: string[]` on `POST /orgs|internal/brands/extract-fields`. Without it the button is inert by construction, because the confirmed value is used TWICE: `profileContext.buildProfileContextBlock` injects it into the prompt under an instruction to PREFER it over the scraped site, and then `multiBrandExtractFields` overlays it back over whatever the model produced. Suppressing one and not the other still hands the user their own previous input, so both suppressions ride the same flag — plus the extraction cache, whose stored value was itself produced under the poisoned prompt.

**The suppression is SCOPED to the listed keys, and that is the whole point.** The 6 Hormozi levers are written FROM the brand's confirmed `services`, so regenerating the levers must still show the model the confirmed services. Never widen this to "drop the confirmed layer for the request" — `extractFields` filters `confirmedFields` by key before building the block, and the overlay loop skips only the listed keys.

**Default behaviour is byte-unchanged.** No flag → the block carries every confirmed field and the overlay applies as before. This is not a mode and must not become the default: the other callers of extract-fields (content generation, internal service reads) want the confirmed value to win.

**A regenerated key is tagged `suggested`, not `confirmed`** — the returned value IS an unsaved auto-extract prefill for the caller to review, and calling it `confirmed` would claim the user validated something they have not seen. **Nothing is persisted or cleared**: `brand_user_fields` is untouched, the confirmed value still wins on every other read, and the user's save (`PUT /orgs/brands/:brandId/user-fields`) is the only thing that overwrites it. The one write is the ephemeral `brand_extracted_fields` slot for the regenerated key, refreshed with the new draft — which is correct, since the stale slot was the poisoned one.

**Every listed key MUST also be in `fields` → 400 (`UnrequestedRegenerateFieldKeyError`), before any work.** A key that is not being extracted has nothing to regenerate, so honouring it silently would tell the caller a field was refreshed when it was never touched.

api-service proxies the body verbatim (`brand.ts` forwards `restBody` with no schema parse), so no gateway change is needed — verified against `origin/main`. Its OpenAPI request schema re-declares a subset and predates `mode` too; that is a doc gap on the gateway, not a runtime one. Regression: `tests/unit/regenerateConfirmedFields.test.ts` (prompt + cache), `tests/unit/regenerateConfirmedOverlay.test.ts` (overlay, provenance, validator), `tests/integration/regenerateConfirmedFields.test.ts`.

## Two-layer brand fields: `brand_user_fields` (confirmed, durable) vs `brand_extracted_fields` (auto, 3-day TTL) + provenance

Brand fields are TWO layers, and every field returned to a consumer carries a **provenance** tag:

- **7 user-facing "confirmed" fields** — `services`, `dreamOutcome`, `perceivedLikelihood`, `socialProof`, `riskReversal`, `urgency`, `scarcity` (hardcoded `USER_FACING_FIELD_KEYS` in `src/services/brandUserFieldsService.ts`). The user validates these in the dashboard; they persist in **`brand_user_fields`** (one row per `(brand_id, field_key)`, DB CHECK on the 7 keys, NO TTL, `value` jsonb). `dreamOutcome` REPLACED the old `valueProposition` in the user-facing set — `valueProposition` is now a pure backend-extract field only (don't reintroduce it as user-facing; the icpSuggestion denylist etc. still reference it legitimately).
- **Everything else** = auto-extracted, ephemeral 3-day cache on `brand_extracted_fields` (unchanged; `CACHE_DURATION_MS` untouched).
- **Provenance**: `confirmed` (a user-facing field with a saved `brand_user_fields` value) | `suggested` (a user-facing field NOT yet confirmed — value = the auto-extract prefill) | `extracted` (a pure backend field).

**Endpoints** (`src/routes/user-fields.routes.ts`, orgRouter, mounted in `index.ts` AND `tests/helpers/test-app.ts`):
- `GET /orgs/brands/:brandId/user-fields` → `{ fields: { <key>: { value, provenance } } }` for all 7 keys. Confirmed value wins; else most-recent NON-EXPIRED `brand_extracted_fields` prefill (campaign_id IS NULL, expires_at NULL-or-future), else null. Does NOT trigger extraction.
- `PUT /orgs/brands/:brandId/user-fields` body `{ fields: Record<key,value> }` → `upsertUserFields` (validates every key ∈ the 7 → 400 `UnknownUserFieldKeyError` on any unknown key, NOTHING written), returns the GET shape.
- `POST /orgs/brands/extract-fields` response gained an ADDITIVE sibling `provenance: Record<key, 'confirmed'|'suggested'|'extracted'>` (built in `multiBrandFieldExtractionService`). Confirmed values overlay `fields[key].value` (single brand) + `byBrand[domain][key].value`; the existing `fields` value SHAPE is unchanged (content-generation-service reads `fields` directly and must keep working). A user-facing key tags `confirmed` only when EVERY brand in the request has a confirmed value, else `suggested`.

`brandProfileService.getByBrandId` now returns `{ current: { fields }, hasConfirmed, confirmedFields }` (was `{ current: version|null, versions[] }`). `current.fields` = confirmed overlaid on the derived-from-extracted fields; `confirmedFields` = the confirmed layer alone (the ONLY client-validated truth injected into the extraction prompt — `profileContext.buildProfileContextBlock` gates on `hasConfirmed`, NOT the merged fields, so we never feed our own past extractions back as authoritative). The versioned `brand_profile_versions` table + the standalone `/orgs/brands/:brandId/brand-profile` GET/POST were DROPPED (migration `0041`); the new confirmed store is the replacement. (A temporary backward-compat shim re-exposed `/orgs/brands/:brandId/brand-profile` over `brand_user_fields` while the prod dashboard + features-service migrated; it has since been fully removed — the only endpoints now are `/user-fields` GET/PUT. Do NOT re-add a brand-profile route.)

**Cron**: `index.ts` runs a daily `setInterval` (24h, + one run 60s after boot) AFTER `app.listen()` deleting `brand_extracted_fields WHERE expires_at < NOW()`. Confirmed rows live in `brand_user_fields` (different table) so they're never touched. Reference: PR (this branch).
